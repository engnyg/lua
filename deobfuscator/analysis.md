## 1 概述

`kicia.lua` 是一個已經被**反編譯**過的 Roblox 腳本。它原本由 Luarmor 保護（檔案中有 `LUARMOR_SkipAntidebugDevMode`、`LUARMOR_AllowKeyCheckSkip`、`ff97f23b97f93792992999` 等特徵），反編譯後留下以下幾層混淆：

| 部分 | 狀態 | 例子 |
|---|---|---|
| 遊戲功能程式碼 | 反編譯後大多已是明文 | `AddToggle`（619 處）、`AddDropdown`、`fighterState`、`Ragebot`、`AutoStrafe`、`CylinderHandleAdornment`、`XRayShaded` |
| 字串常數 | **加密**，是本工具的主要目標 | `up0[up1("\248Ot\178…", 11388453333358)]` |
| 識別字 | 全部被改成編號 | `f1`、`v184`、`p35`、`up0` |

解密後可以看到，加密字串**大多屬於 Luarmor 的授權載入器**：驗證伺服器（`eu1-roblox-auth.luarmor.net` 等十多台）、WebSocket 心跳（`] [PING] Client ---> Server`）、錯誤訊息（`You are blacklisted`、`This script is outdated! Try using the latest version.`）、版本號（`"3.4"`）。

## 2 混淆層次

### 2.1 識別字重新命名

| 原本 | 混淆後 | 例子 |
|---|---|---|
| 函式 | `f<N>`（全檔唯一編號） | `f1`、`f297`、`f10422` |
| 區域變數 | `v<N>` | `v184` |
| 參數 | `p<N>` | `p35` |
| 上值（upvalue） | `up<N>`（每個函式各自從 0 編號） | `up0`、`up5` |

`up<N>` 的編號是**每個函式各自獨立**的：同一個字串快取表，在 A 函式裡叫 `up0`，在 B 函式裡可能叫 `up2`。所以不能只找 `up0[up1(…)]`，必須接受任意名稱（見第 9 節）。

### 2.2 字串加密

每個字串常數都被寫成：

```lua
cache[decrypt(ciphertext, key)]
```

`decrypt` 會把明文算出來存進 `cache[key]`，然後**回傳 key 本身**，所以外面的 `cache[…]` 取到的就是明文。

實際解密例子（全部由工具算出，可在 `kicia_deobfuscated_strings.json` 查到）：

| 密文 | key | 明文 |
|---|---|---|
| `",\196P\\"` | 10051603965073 | `"PONG"` |
| `"\159\11\208\29\209"` | 9071247761664 | `"match"` |
| `"\20/x-\133"` | 7497094208326 | `"table"` |
| `"\248Ot\178\26\"\163W\188"` | 11388453333358 | `"Websocket"` |
| `"6\143K\188=\r\226…"` | 2340828612740 | `"eu1-roblox-auth.luarmor.net"` |
| `"\233\191\12"` | 22757578724042 | `"3.4"` |

### 2.3 控制流程混淆

插入恆真或恆假的條件、只跑一次的 `repeat` 迴圈、以及馬上被覆蓋的暫存指定，見第 6 節。

### 2.4 反除錯與垃圾程式碼

`(nil)()` 當機陷阱、丟棄結果的 `bit32`/`math` 呼叫、`local _ = <運算式>`、空函式，見第 7 節。

## 3 字串加密演算法

### 3.1 解密函式

檔案裡有兩份相同的解密器：`f10149` 內的 `f10421`/`f10422`（Luarmor 載入器本體），以及 `f1` 內的副本 `f215`/`f89`。以 `f10422` 為例：

```lua
local function f10422(p262, p263)          -- (密文, key)
    local t302 = t301                      -- 明文快取
    if not t302[p263] then
        f10418 = {}                        -- 清空位元組緩衝區
        local t303 = t299                  -- 字元表（第 5 節）
        f10420 = p263 % 35184372088832     -- 45 位元狀態 = key mod 2^45
        f10419 = p263 % 255 + 2            -- 8 位元狀態 = key mod 255 + 2
        t302[p263] = ""
        local v307 = 77                    -- 前一個明文位元組的初始值
        for v308 = 1, #p262 do
            v307 = (string.byte(p262, v308) + f10421() + v307) % 256
            t302[p263] = t302[p263] .. t303[v307 + 1]
        end
    end
    return p263                            -- 回傳 key，外層用它查快取
end
```

### 3.2 金鑰流產生器（f10421 / f215）

```lua
local function f10421()
    if #f10418 == 0 then
        f10420 = (f10420 * 149 + 4033097371307) % 35184372088832   -- 2^45
        repeat
            f10419 = f10419 * 37 % 257
        until f10419 ~= 1
        local v305 = f10419 % 32
        local v306 = floor(f10420 / 2 ^ (13 - (f10419 - v305) / 32)) % 4294967296 / 2 ^ v305
        local _ = floor(v306 % 1 * 4294967296) + floor(v306)
        f10418 = _G["table.create"](4)      -- ← 反編譯器沒還原的部分
    end
    return (table.remove(f10418))
end
```

反編譯器把最後幾行弄壞了：`local _ = …` 其實是一個 32 位元亂數，`table.create(4)` 那行原本是把它拆成 4 個位元組放進緩衝區。這是公開的 **Prometheus** 混淆器字串加密的寫法，完整形式是：

```lua
local rnd  = floor(v306 % 1 * 2^32) + floor(v306)
local low  = rnd % 65536
local high = (rnd - low) / 65536
buffer = { low % 256, (low - low % 256) / 256, high % 256, (high - high % 256) / 256 }
```

`table.remove` 從尾端取，所以每 4 個位元組的輸出順序是 `high>>8`、`high&255`、`low>>8`、`low&255`。

### 3.3 數學描述

```
s45 ← key mod 2^45
s8  ← key mod 255 + 2
prev ← 77

需要新的 4 個位元組時：
    s45 ← (149·s45 + 4033097371307) mod 2^45
    重複 s8 ← 37·s8 mod 257，直到 s8 ≠ 1
    r   ← s8 mod 32
    n   ← (⌊s45 / 2^(13 − (s8 − r)/32)⌋ mod 2^32) / 2^r
    rnd ← ⌊frac(n)·2^32⌋ + ⌊n⌋
    緩衝區 ← rnd 的 4 個位元組（從高位開始取）

每個密文位元組 b：
    prev ← (b + 下一個金鑰位元組 + prev) mod 256
    輸出 chr(prev)
```

加密就是反過來：`c = (p − k − prev) mod 256`，其中 `prev` 是前一個**明文**位元組。`test_deobfuscator.py` 用這個加密函式產生測試資料。

### 3.4 Python 實作

```python
def keystream(key):
    s45, s8, buf = key % 2**45, key % 255 + 2, []
    while True:
        if not buf:
            s45 = (s45 * 149 + 4033097371307) % 2**45
            s8 = s8 * 37 % 257
            while s8 == 1:
                s8 = s8 * 37 % 257
            r = s8 % 32
            n = (s45 // 2 ** (13 - (s8 - r) // 32)) % 2**32 / 2 ** r
            rnd = int(n % 1 * 2**32) + int(n)
            lo, hi = rnd % 65536, rnd // 65536
            buf = [lo % 256, lo // 256, hi % 256, hi // 256]
        yield buf.pop()

def decrypt(cipher: bytes, key: int) -> bytes:
    out, prev = bytearray(), 77
    for b, k in zip(cipher, keystream(key)):
        prev = (b + k + prev) % 256
        out.append(prev)
    return bytes(out)
```

`(s8 - r) // 32` 一定整除；`n` 的小數部分最多 31 位元，在 IEEE 754 double 裡是精確的，所以 Python 和 Lua 的結果逐位元相同。

## 4 解謎過程：怎麼找到正確的亂數產生器

這一節記錄第一版分析**犯過的錯**，以及怎麼修正的。

1. **找到解密器**：`up0[up1(…)]` 出現幾千次，追 `up1` 的定義找到 `f89`，它的結構很清楚：用 key 設定兩個狀態、逐位元組呼叫 `up5()`、查表。
2. **第一版的錯誤**：檔案裡另外有 `f65`/`f66`（還有 `f120`/`f121`）這組使用 `1103515245 / 12345 / 99999999` 的 LCG。第一版誤以為 `up5` 就是它，還自己補了一個 `add = x % step` 來湊合 `up4`。結果所有解密輸出都是亂碼，文件卻把原因歸咎於「字元表是執行時才打亂的」。
3. **正確做法**：`f89` 設定的兩個上值是 `key % 2^45` 和 `key % 255 + 2`，所以要找的是**用同樣兩個常數**的函式。搜尋 `35184372088832`，找到 `f215`（第 2405 行）和 `f10421`（第 158619 行）：`(s * 149 + 4033097371307) % 2^45` 和 `s * 37 % 257`，正是 f89 設定的那兩個狀態。
4. **補回反編譯器弄壞的部分**：`f215` 裡 `local _ = floor(…) + floor(…)` 算了一個值卻丟掉，下一行建立長度 4 的表。對照 Prometheus 的原始碼，確認這裡是「拆成 4 個位元組」。
5. **驗證**：用已知向量測試，`("\20/x-\133", 7497094208326)` 解出 `table`，`("\158\226\202\\\232\159", 458501751211)` 解出 `random`。全部 404 個不同的字串都是合法的 UTF-8，內容也都有意義（網址、API 名稱、錯誤訊息），可以確定演算法正確。

另外，`f65`/`f120` 是**另一個**亂數產生器，`f122` 用它產生一個 16 字元的識別碼（字母表 `qwertyuiopasdfghjklzxcvbnm098765` 剛好 32 個字元，每字元 5 位元），存進 `UserGameSettings:SetTutorialState`，和字串加密無關。

## 5 字元表

第 158603–158616 行建立 `t299`：

```lua
for v302 = 1, 256 do t300[v302] = v302 end
repeat
    local v303 = math.random(1, #t300)
    local v304 = table.remove(t300, v303)
    t299[v304] = string.char(v304 - 1)
until #t300 == 0
```

雖然用了 `math.random`，但隨機的只是**填表的順序**，每一格的內容永遠是 `t299[i] = string.char(i - 1)`。所以這是**恆等映射**，`t299[v + 1]` 就是 `chr(v)`，解密時完全不需要這張表。全檔只有這一處建立字元表。

（第一版文件說字元表是打亂的、恆等映射只有約 70% 準確，這是錯的。）

## 9 工具的處理步驟

所有檔案都以 **latin-1** 讀寫，每個位元組對應一個字元，所以沒有改動的部分會逐位元組保留（包含 CRLF 換行）。

### 步驟 1：找出解密呼叫（三種寫法）

| 寫法 | 例子 | 處理 |
|---|---|---|
| 字面值 | `up2[up3("\20", 25372219857997)]` | 名稱不限（`\w+\[\w+\("…", KEY\)\]`），key ≥ 10⁹ |
| 暫存呼叫 | `f12 = f12("…", K)` 下一行接 `f12 = up2[f12]` | 兩行合成 `f12 = "明文"` |
| 變數參數 | `v6 = "…"` … `up2[up3(v6, K)]` | 往上最多 8 行、在同一個直線區塊內找變數的字面值指定；key 變數可追蹤一層別名 |

變數形式的回溯遇到 `end`、`else`、`then`、`do`、`function`、迴圈等區塊邊界，或中途有其他地方用到該變數，就放棄，不做替換。位於字串或註解內的匹配會被略過（工具內有一個簡易 Lua 詞法分析器）。

### 步驟 2：解析密文

`parse_lua_string` 完整支援 Lua 的跳脫字元：`\a \b \f \n \r \t \v \\ \" \'`、`\ddd`（十進位，超過 255 報錯）、`\xXX`、`\u{XXX}`、`\z`、反斜線加換行。解析失敗的位置會保持原樣，並列入 `undecodable literals` 計數。

### 步驟 3：輸出安全的字串字面值

`lua_quote` 只輸出 ASCII：`"` 和 `\` 會跳脫，換行、Tab 用 `\n`、`\t`，其他控制字元和 ≥ 0x80 的位元組用三位數 `\ddd`（避免後面接數字時產生歧義）。

如果原本的運算式後面接 `:`、`.`、`(`、`[`、`{` 或字串，例如 `up0[up1(…)]:Close()`，就包成 `("Websocket"):Close()`，因為 Lua 不允許 `"s":f()`。如果它剛好位於語句開頭，再加上 `;`，避免 Lua 把它當成對上一行的函式呼叫。

### 步驟 4：刪除垃圾程式碼

依第 7 節的規則，只刪除能證明沒有副作用的語句。

### 步驟 5：輸出

- `<輸出>.lua`：反混淆後的程式碼
- `<輸出去掉副檔名>_strings.json`：每個不同的 (密文, key)，包含 `key`、`cipher`、`plain`（Lua 字面值）、`text`（UTF-8 解碼後的文字）、`sites`（出現次數）

輸入、輸出、JSON 三個路徑必須彼此不同，否則直接拒絕執行，不會覆寫任何檔案。

## 11 已知限制

| 限制 | 說明 |
|---|---|
| 反編譯殘留 `up3;(` | 原始檔第 13 行本身就不是合法的 Lua/Luau。這不是加密造成的，`deobfuscator.py` 不猜測原意，保持原樣；`optimize.py` 會依反編譯器的慣例還原（第 14 節） |
| 解密器本體 | `f215`/`f10421` 被反編譯器弄壞（少了拆位元組的步驟）。`deobfuscator.py` 是靜態解密，不受影響；`optimize.py` 會補回這一步（第 14 節） |
| 剩下 9 處 `X[Y("…")]` | 例如 `p304[p306("Wrap")]`，本來就是明文，不是加密呼叫 |
| 多行的 `local _ = …` | 需要完整解析運算式才能安全刪除，目前保留 |
| `local _` 刪除後的寫入 | 全檔從未讀取 `_`；但如果同一範圍後面有 `a, _ = f()`，刪掉 `local _` 後這個寫入會落到外層的 `_`（可能是全域變數）。因為沒有任何地方讀取它，程式行為不變 |
| 識別字 | `f`/`v`/`p`/`up` 編號名稱仍需人工依上下文命名；`optimize.py` 只自動處理有字面依據的部分（第 15 節） |

## 12 檔案本質：函式原型傾印

`up0`–`up101` 在整份檔案裡出現超過一萬四千次，**卻從來沒有被宣告過**。作用域解析（`luau-tool resolve`）的結果是：全檔有 16,088 個 `upN` 引用找不到宣告，其餘找不到宣告的名稱都是 Roblox／Lua 的全域變數（`table`、`Instance`、`game`…）。

原因是反編譯器把每個函式原型各自反編譯、再依巢狀位置排在一起：

- `f1` 本體只有一連串 `local function fN` 和最後的 `return f2, f3, …`，沒有任何資料變數。它的每個子函式都是單獨反編譯的單位，原本綁定的外層變數（例如字串快取表）不存在於檔案裡，只剩 `upN` 這個編號。
- 每個函式原型的 `upN` 都是**各自獨立編號**的：同一個東西在外層 `f5427` 叫 `up0`（有 `bindColor` 等方法），在它內層的 `f5429` 則叫 `up2`；而外層的 `up2` 是另一個可以呼叫的函式。巢狀函式引用外層的區域變數時，則直接用真正的名稱（例如 `f66` 直接用 `v125`）。
- 各個 v/t/p 編號名稱在同一個頂層函式裡是唯一的（36,902 個宣告，沒有重複）。

**結論：這份檔案無法直接執行**，還原殘留也不能讓它變得可執行。它的價值在於閱讀和分析，所以第二階段的目標是**可讀性**，而不是執行速度。

## 13 不透明條件：為什麼不刪除

全檔有 133 處 `V = not not C`。照字面解讀，其中 28 段程式碼永遠不會執行。原本的計畫是把這些死碼刪掉，但檢查每一段的內容後發現，**反編譯器輸出的 `not not false` 不可信**：

| 位置 | 被 `not not false` 包住的內容 | 如果真的不執行 |
|---|---|---|
| `f119`、`f121`、`f124`、載入器裡的 `f10415` | 亂數產生器的狀態更新（和沒被包住的 `f66` 完全相同） | 下一行 `v = nil * 數字`，**每次呼叫都會出錯**；而 `f122` 產生新的識別碼時會呼叫 `f124` 80 次 |
| `f7515` 等 4 處 | `fN = unpack; v = …; v = 1` | 下一行 `return (fN(…))` 會呼叫 nil，**必定出錯** |
| `f8147` 等 2 處 | `t154 = {}` | 下一行 `t154.c = …` 會對 nil 取欄位，**必定出錯** |

這些函式都有明確用途，照字面解讀卻「一定會當掉」，所以真實程式裡這些分支應該會執行，是反編譯器把條件還原錯了。另一方面，也有 `not not false` 確實是假的例子：`f1866` 整個函式本體都包在 `if not v2 then` 裡，如果 `v2` 是真，整個函式就什麼都不做。

所以 `not not false` 實際上代表「反編譯器算不出來的條件」，每一處的真實值都可能不同。至於 `not not true`，目前的證據（`f42` 的 `while true do` 迴圈）顯示它是對的，但證據只有一處。

依使用者的決定，`optimize.py` **不刪除也不修改任何不透明條件**，只在報告裡列出每一處。對於照字面解讀不會執行的程式碼，報告會判斷它像哪一類：

| 判斷 | 條件 | 段數 |
|---|---|---|
| 陷阱 | 含有 `(nil)`、`-nil`、`[nil]`、`(false)(…)` 這類必定出錯的寫法 | 9 |
| 只有流程控制 | 只有 `break` / `return` | 2 |
| 像真實邏輯 | 其他 | 17 |

完整清單見 `kicia_optimized_report.md`。

## 14 還原反編譯殘留

| 殘留 | 處數 | 還原成 | 依據 |
|---|---|---|---|
| `_G["table.create"](n)` | 2,683 | `table.create(n)` | Luau 的內建函式被反編譯器寫成全域表查詢；照字面執行會拿到 nil |
| `_G["bit32.bxor"]` | 53 | `bit32.bxor` | 同上 |
| `up3;(…)` | 1 | `up3(…)` | 分號插錯位置，原本是函式呼叫 |
| 解密器的 4 位元組拆分 | 2 | 見下 | 對照 Prometheus 原始碼 |

解密器（`f215`、`f10421`）的最後兩行原本是：

```lua
local _ = floor(v306 % 1 * 4294967296) + floor(v306)
f10418 = table.create(4)
```

還原為：

```lua
local rnd = floor(v306 % 1 * 4294967296) + floor(v306)
local lo = rnd % 65536
local hi = (rnd - lo) / 65536
f10418 = { lo % 256, (lo - lo % 256) / 256, hi % 256, (hi - hi % 256) / 256 }
```

**驗證**：把還原後的字元表、`f10421`、`f10422` 原封不動從輸出檔抽出來，在真正的 Lua 5.4 裡執行，`("\20/x-\133", 7497094208326)` 解出 `table`，`("\158\226\202\\\232\159", 458501751211)` 解出 `random`，和 Python 實作的結果相同。

還原後，整份檔案第一次能被 Luau 解析器（full-moon）完整解析，0 個錯誤。

`table.create(n)` 的內容也值得注意：UI 設定裡常見的 `Config = table.create(2)`，原本很可能是有兩個元素的表格，內容在反編譯時就遺失了，無法還原。

## 15 自動改名

### 15.1 範圍

- **不改名**：`f1`（Luarmor 執行環境：位元組碼反序列化、雜湊、驗證連線、TutorialState 識別碼），以及載入器序段（包含 `LUARMOR_*` 的函式開頭，到它最後一個 `while true do` 為止）。這些是第三方授權服務的程式碼，不是腳本本身，本工具不替它的授權檢查與反竄改機制做標註。範圍由程式碼特徵自動推算，不寫死行號。
- **改名**：其餘部分，也就是遊戲功能模組（Triggerbot、Chams、Replay、UI 等）。

### 15.2 規則

只改反編譯器產生的 `vN` / `tN` / `fN` 名稱，而且每個名字都要有字面依據：

| 規則 | 依據 | 例子 | 數量 |
|---|---|---|---|
| Instance.new | `local v = Instance.new("UICorner")` | `uiCorner` | 1,212 |
| field | `local v = a.b.Character` | `character` | 1,864 |
| string index | `local v = a["Host"]` | `host` | 2 |
| signal handler | 函式被傳給 `x.RenderStepped:Connect(f)`，而且只對應一個訊號 | `onRenderStepped` | 153 |
| assigned to field | 函式被存進欄位 `t._reconcile = f`，而且只有這一個欄位名稱 | `_reconcile` | 8 |
| UI section title | `local t = { Title = "Auto Queue" }` 下一行 `local s = AddSection(p, t)` | `autoQueueSection` | 222 |

另外：

- 反編譯器會重複使用同一個變數名稱存放不同用途的值（暫存器重用）。只要變數在宣告之後還被重新賦值，就不套用 field / assigned to field 規則，避免名稱只對應其中一種用途。
- 名稱撞到時加數字尾碼（`character2`）；如果名稱本身以數字結尾，改用 `_2`。
- 不使用 Lua 關鍵字，也不使用 `self`、`continue`、`type`、`export`。

### 15.3 安全性

1. `luau-tool resolve` 解析每個變數名稱的作用域：`local`、參數、`for` 變數、`repeat … until` 的特殊作用域、`local x = x` 右邊指向外層、方法的隱含 `self`、以及欄位名稱不算變數。
2. 新名稱不能出現在該變數所在函式的任何變數名稱中（包含全域變數的引用），避免遮蔽或捕獲。
3. **改名後重新解析整份檔案**，逐一比對每個名稱是宣告還是引用、以及引用指向哪個宣告。只要有任何一處不同，就中止，不寫出檔案。這一步直接證明改名沒有改變任何變數的綁定關係。

完整的 3,461 筆對照（行號、舊名、新名、規則）在 `kicia_optimized_report.json` 的 `renames`。
